# Архитектура

## 1. Обзор

Spyfall — клиент-серверное веб-приложение с real-time взаимодействием.

```
┌──────────────┐        HTTP / WS        ┌──────────────┐
│   Frontend   │ ◄─────────────────────► │   Backend    │
│  React + TS  │                         │   Go (std)   │
│  Vite        │                         │   net/http   │
└──────────────┘                         └──────┬───────┘
                                                │
                                         In-memory state
                                        (no external DB)
```

## 2. Технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Frontend | React 19, TypeScript, Vite 7 | Уже инициализирован в `frontend/`. SPA с компонентным подходом. |
| Backend | Go 1.22, стандартная библиотека (`net/http`) | Уже инициализирован в `backend/`. Минимальные зависимости, встроенный HTTP-сервер. |
| Транспорт (real-time) | WebSocket (`golang.org/x/net/websocket` или `nhooyr.io/websocket`) | Игра требует мгновенной доставки событий всем участникам лобби (смена хода, голосование, результаты). |
| Транспорт (управление) | REST over HTTP/JSON | Создание лобби, присоединение — одноразовые запросы, не требующие постоянного соединения. |
| Хранение состояния | In-memory (Go maps/structs, защищённые мьютексами) | MVP не требует персистентности. Перезапуск сервера сбрасывает все лобби. |
| Пакетный менеджер (frontend) | pnpm 9.15.4 | Уже настроен в `frontend/package.json`. |
| CI/CD | GitHub Actions | Уже настроен в `.github/workflows/rebuild-deploy.yml`. |

## 3. Протокол взаимодействия

### REST (HTTP JSON)

Используется для операций, не требующих real-time:

- Создание лобби → `POST /api/lobbies`
- Присоединение к лобби → `POST /api/lobbies/{code}/join`
- Health check → `GET /readyz` (уже реализован)

### WebSocket

Используется для всей in-game коммуникации после подключения к лобби:

- Клиент устанавливает WS-соединение: `ws://<host>/api/lobbies/{code}/ws?playerId={id}`
- Сервер отправляет события всем клиентам в лобби (broadcast)
- Клиент отправляет команды (действия игрока) через то же соединение

Формат сообщений — JSON:

```json
{
  "type": "event_type",
  "payload": { ... }
}
```

Подробные схемы событий и команд описаны в [api-contract.md](api-contract.md).

## 4. Управление состоянием

### Backend

Всё состояние хранится в памяти процесса:

- `map[string]*Lobby` — хранилище лобби, ключ — invite code
- Каждый `Lobby` содержит список игроков, настройки и текущую `Session`
- Доступ к shared state защищён `sync.RWMutex`
- При изменении состояния сервер рассылает обновлённый snapshot всем подключённым клиентам через WebSocket

### Frontend

- Состояние приложения управляется через React Context + `useReducer`
- WebSocket-соединение оборачивается в кастомный хук (`useGameSocket`)
- Входящие WS-события диспатчатся как actions в reducer, обновляя стейт
- Внешние библиотеки для state management (Redux, Zustand) не используются в MVP

## 5. Структура кода

### Backend (`backend/`)

```
backend/
├── main.go              # Точка входа, инициализация HTTP-сервера и роутов
├── go.mod
├── handler/             # HTTP и WS хендлеры (по файлу на ресурс)
│   ├── lobby.go         # REST: создание, присоединение
│   └── ws.go            # WebSocket: upgrade, чтение/запись сообщений
├── game/                # Доменная логика
│   ├── lobby.go         # Lobby, Player, LobbySettings
│   ├── session.go       # Session, фазы игры, переходы состояний
│   └── location.go      # Набор локаций, случайный выбор
├── hub/                 # WebSocket hub — управление соединениями и broadcast
│   └── hub.go
└── docs/
    └── features/
```

### Frontend (`frontend/`)

```
frontend/
├── src/
│   ├── main.tsx
│   ├── App.tsx           # Корневой компонент, маршрутизация
│   ├── pages/            # Страницы (по маршруту)
│   │   ├── Home.tsx      # Главная: создать / присоединиться
│   │   ├── Lobby.tsx     # Экран лобби (ожидание, настройки)
│   │   └── Game.tsx      # Экран игры (фазы вопросов, голосования, результатов)
│   ├── components/       # Переиспользуемые UI-компоненты
│   ├── hooks/            # Кастомные хуки
│   │   └── useGameSocket.ts
│   ├── context/          # React Context для глобального стейта
│   │   └── GameContext.tsx
│   ├── types/            # TypeScript типы, дублирующие backend-модели
│   │   └── game.ts
│   └── utils/            # Вспомогательные функции
├── docs/
│   └── features/
└── ...
```

## 6. Маршрутизация (Frontend)

SPA с клиентской маршрутизацией (React Router или аналог):

| Маршрут | Страница | Описание |
|---|---|---|
| `/` | Home | Создание лобби или ввод кода приглашения |
| `/lobby/{code}` | Lobby | Экран ожидания, настройки, готовность |
| `/game/{code}` | Game | Активная сессия (все фазы игры) |

## 7. Деплой

- Frontend собирается в статику (`pnpm run build` → `dist/`)
- Backend компилируется в бинарник (`go build -o bin/server .`)
- GitHub Actions workflow (`.github/workflows/rebuild-deploy.yml`) уже содержит шаги сборки; шаг деплоя пока placeholder
- В production frontend-статика может раздаваться Go-сервером или отдельным CDN/nginx

## 8. Принципы и ограничения

- **Никаких внешних баз данных** в MVP. Состояние живёт в памяти.
- **Минимум внешних зависимостей** на backend: стандартная библиотека Go + одна библиотека для WebSocket.
- **Без SSR** — фронтенд является чистым SPA.
- **Без аутентификации** — игроки идентифицируются по сгенерированному `playerId` (UUID), который хранится в памяти клиента (sessionStorage).
- **Один шпион** — множество шпионов не поддерживается (см. [rules.md](rules.md), раздел 3.2).
